# Troubleshooting

Common questions and solutions when running the stack, ordered by service. Every section below
is written from an issue that actually occurred and was fixed during the first real Windows
install — the symptom, the cause, and the fix.

Before anything else: **re-run the one-liner.** Every script is idempotent and reconciles an
existing install. On Windows, re-running downloads the bootstrap to `%TEMP%\music-stack-bootstrap`
again, so delete that folder first to make sure you pick up current script code rather than a
cached copy:

```powershell
Remove-Item -Recurse -Force "$env:TEMP\music-stack-bootstrap" -ErrorAction SilentlyContinue
# then re-run the Windows one-liner from the README
```

## Is it running at all?

Three quick checks, one per service:

```powershell
Get-NetTCPConnection -State Listen -LocalPort 4533,8686,8443 -ErrorAction SilentlyContinue |
    Select-Object LocalPort,OwningProcess | Sort-Object LocalPort
```

| Port | Service | Healthy state |
| --- | --- | --- |
| `4533` | Navidrome | listening; `http://localhost:4533` shows a login/setup page |
| `8686` | Lidarr | listening; `http://localhost:8686` shows the dashboard |
| `8443` | qBittorrent WebUI | listening; `http://localhost:8443` shows the WebUI |

## Navidrome

### Navidrome service fails to start / instantly dies ("TOML parse error")

**Cause:** the config file was written with a UTF-8 BOM. Windows PowerShell's `Set-Content
-Encoding UTF8` prepends `EF BB BF`, which Navidrome's TOML parser rejects. This hit the first
real Windows install.

**Fix:** the script now writes all configs BOM-less (and re-runs of current code do too), but for
an already-broken install, strip the BOM and restart:

```powershell
$p = 'C:\ProgramData\music-stack\navidrome.toml'
$bytes = [System.IO.File]::ReadAllBytes($p)
if ($bytes[0] -eq 0xEF -and $bytes[1] -eq 0xBB -and $bytes[2] -eq 0xBF) {
    [System.IO.File]::WriteAllBytes($p, $bytes[3..($bytes.Length-1)])
}
Restart-Service Navidrome
```

Verify the first three bytes are `23 20` (`# `, a comment), not `EF BB BF`.

### Service is "Paused" instead of "Running"

**Cause:** Windows put the service in pause after a crash loop (a crash-looping service is
paused, not stopped). Merely restarting won't hold.

**Fix:** continue the paused service:

```powershell
sc.exe continue Navidrome
Get-Service Navidrome   # expect: Running
```

Check `C:\ProgramData\music-stack\logs\navidrome.log` (or wherever `NAVIDROME_PORT` logging
lands) for the underlying error — usually the BOM issue above.

## Lidarr

### Lidarr service fails to start ("Error 2", service can't find the binary)

**Cause:** the Servarr Windows installer puts the binaries in `C:\ProgramData\Lidarr\bin\`, not
`C:\Program Files\Lidarr\`. A script or manual NSSM entry pointing at
`C:\Program Files\Lidarr\Lidarr.exe` can never start.

**Fix:** repoint the NSSM service at the real binary and tell it where its data lives:

```powershell
& 'C:\Program Files\NSSM\nssm.exe' set Lidarr AppDirectory 'C:\ProgramData\Lidarr\bin'
& 'C:\Program Files\NSSM\nssm.exe' set Lidarr Application 'C:\ProgramData\Lidarr\bin\Lidarr.exe'
& 'C:\Program Files\NSSM\nssm.exe' set Lidarr AppParameters ' -data=C:\ProgramData\music-stack\lidarr'
& 'C:\Program Files\NSSM\nssm.exe' set Lidarr AppStdout 'C:\ProgramData\music-stack\logs\lidarr.log'
& 'C:\Program Files\NSSM\nssm.exe' set Lidarr AppStderr 'C:\ProgramData\music-stack\logs\lidarr.log'
& 'C:\Program Files\NSSM\nssm.exe' set Lidarr AppRotateFiles 1
& 'C:\Program Files\NSSM\nssm.exe' set Lidarr AppRotateBytes 10485760
& 'C:\Program Files\NSSM\nssm.exe' set Lidarr Start SERVICE_AUTO_START
Start-Service Lidarr
```

The `-data=...` argument is what keeps Lidarr's database in `DATA_DIR` instead of inside its
install folder.

### "Unexpected status SERVICE_STOP_PENDING" when restarting via NSSM

**Cause:** `nssm restart` issues a STOP, and if the stop doesn't complete in time NSSM aborts —
leaving the service stopped. This is an NSSM timing behavior, not a stack bug.

**Fix:** start it explicitly:

```powershell
Start-Service Lidarr
```

Then confirm it is listening: `Get-NetTCPConnection -LocalPort 8686 -State Listen`.

### Health check: "Please update your API key to be at least 20 characters long"

**Cause:** Lidarr v3 requires API keys of **at least 20 characters**. A short key means it was
generated by old script code (the first-generation generator produced only 16 characters). The
current scripts always generate 32 hex characters, but a pre-existing install keeps its short
key.

**Fix:** generate a 32-char key, write it into Lidarr's `config.xml`, restart, and update
`settings.env` so future runs stay consistent:

```powershell
$key = -join (1..32 | ForEach-Object { '{0:x}' -f (Get-Random -Maximum 16) })
$xml = 'C:\ProgramData\music-stack\lidarr\config.xml'
$content = (Get-Content $xml -Raw) -replace '<ApiKey>.*?</ApiKey>', "<ApiKey>$key</ApiKey>"
[System.IO.File]::WriteAllText($xml, $content, (New-Object System.Text.UTF8Encoding($false)))
Start-Service Lidarr
```

(Write it BOM-less — see `MAINTENANCE.md` for why configs must never get a UTF-8 BOM.)

Then verify the warning is gone: `http://localhost:8686` → Health, or
`Invoke-RestMethod http://127.0.0.1:8686/api/v1/health -Headers @{ 'X-Api-Key' = $key }`.

### Health check: "No indexers available with RSS sync / Automatic Search enabled"

**Expected, not a bug.** Indexers are manual by design (they need your tracker credentials).
Until you add at least one indexer under **Settings → Indexers** (or via `config/indexers.json`),
Lidarr cannot grab anything automatically. Adding a private music tracker / usenet indexer is
what makes the "complete my library" workflow actually work.

## qBittorrent WebUI

The qBittorrent symptoms below are the deepest rabbit hole this project has been through, and
all of them are version/behavior traps rather than config mistakes. If the WebUI port (`8443`)
is not listening, check them in order.

### WebUI port not listening, tray icon shows a "Legal Notice" dialog

**Cause:** first run, qBittorrent shows a Legal Notice dialog that blocks startup — no WebUI
binds until it is accepted. Pre-seeding `[LegalNotice] Accepted=true` in the config is **not**
enough on some versions; the dialog still appears.

**Fix:** launch qBittorrent with the CLI flag that skips it:

```powershell
Start-Process 'C:\Program Files\qBittorrent\qbittorrent.exe' -ArgumentList '--confirm-legal-notice'
```

The scripts now always launch with this flag.

### WebUI port not listening even though the dialog is gone and torrent ports are up

**Cause:** qBittorrent's config file is not being read at all. **v5.2 renamed the Windows config
file** from `qBittorrent.conf` to `qBittorrent.ini` (`%APPDATA%\qBittorrent\`). Pre-seeding only
`.conf` is silently ignored on Windows v5.2+. (Linux/macOS still use `.conf`.) Both files may
exist side by side — the `.ini` is the one that matters.

**Fix:** check what actually lives there:

```powershell
Get-ChildItem "$env:APPDATA\qBittorrent" | Select-Object Name,Length,LastWriteTime
```

The current scripts pre-seed **both** files, so this is self-healing on re-run.

### Log says "WebUI: Credentials are not set", WebUI refuses to start

**Cause:** qBittorrent v5.x reads **only** `WebUI\Password_PBKDF2`; the pre-v5 MD5 hash in
`WebUI\Password` is ignored. With no accepted credential the WebUI refuses to bind — this is a
hard refusal (the port stays closed), not a fallback to a default password. Log location:
`%LOCALAPPDATA%\qBittorrent\logs\qbittorrent.log`.

**Fix:** the scripts pre-seed both keys (MD5 for ≤5.1, PBKDF2 for ≥5.0) in the config. For a
live machine, re-running the setup script regenerates the config with the PBKDF2 value. The
PBKDF2 value is `base64(16 random bytes):base64(PBKDF2-HMAC-SHA512(password, salt, 100000,
64))` stored as `WebUI\Password_PBKDF2=@ByteArray(<salt>:<key>)` — see `MAINTENANCE.md` for the
exact derivation if you need to reproduce it by hand.

Verify the WebUI is truly reachable with credentials, not just bound:

```powershell
(Invoke-WebRequest -Uri 'http://127.0.0.1:8443/api/v2/auth/login' -Method Post `
    -Body @{ username = 'admin'; password = '<your QBIT_PASSWORD>' } -UseBasicParsing).Content
```

A `sid=...` cookie in the response means the credential was accepted.

## Lidarr API / post-config

### `POST /rootfolder` → HTTP 400 "Folder is not writable by user '...$'"

**Cause:** Lidarr validates a root folder by probing it *as the account the service runs as*
(the machine account, e.g. `DESKTOP-XXXXXXX$`). On a workgroup machine you cannot grant an
explicit machine-account ACE — `icacls /grant "DESKTOP-XXXXXXX$:..."` fails with *"No mapping
between account names and security IDs"*.

**Fix:** grant Everyone modify on the music folder and download dir (this is what the scripts
do):

```powershell
icacls C:\Music /grant 'Everyone:(OI)(CI)(M)' /T
icacls 'C:\ProgramData\music-stack\downloads' /grant 'Everyone:(OI)(CI)(M)' /T
```

### `POST /rootfolder` → HTTP 400 "Name must not be empty" / "Default Metadata Profile Id must be greater than 0"

**Cause:** Lidarr v3 requires a **full** `RootFolderResource` body. A minimal `{"path": ...}`
that v2 accepted is rejected by v3.

**Fix:** send the complete body. The script does this automatically — for a manual call, include
`name` (the folder's leaf name), `defaultMetadataProfileId`, `defaultQualityProfileId`,
`defaultMonitorOption`, `defaultNewItemMonitorOption`, and `defaultTags` (the profile ids come
from `GET /qualityprofile` and `GET /metadataprofile`).

## Post-configuration by hand

If the automatic post-config didn't run (or you changed a port), run it manually. It is
idempotent:

```powershell
py scripts\common\configure-lidarr.py --settings settings.env `
    --api-key <LIDARR_API_KEY> --port 8686 `
    --music-dir C:\Music --qbit-user admin --qbit-password <QBIT_PASSWORD> --qbit-port 8443
```

When installed via the one-liner, the settings file lives at
`%TEMP%\music-stack-bootstrap\music-stack-main\settings.env` — pass that path to `--settings`.

## Still stuck?

1. Check the service is listening (§ "Is it running at all?").
2. Check each service's own log:
   - Navidrome: `C:\ProgramData\music-stack\logs\navidrome.log` (Windows)
   - Lidarr: NSSM stdout/stderr → `C:\ProgramData\music-stack\logs\lidarr.log` (Windows)
   - qBittorrent: `%LOCALAPPDATA%\qBittorrent\logs\qbittorrent.log`
3. Re-run the one-liner (delete `%TEMP%\music-stack-bootstrap` first on Windows).
4. Open a GitHub issue with: the output of the three-port check, the service statuses
   (`Get-Service Navidrome,Lidarr`), your Windows version, and the relevant log tail.
